# 项目规则：统一编程流程与交付标准

本规则结合本项目已有的中文注释规范、基于技能的实现流程、6A 工作流、敏捷 5S 个人规则，以及 Karpathy 风格的 Claude 代码指导原则，指导所有代码开发、验证、交付和审查工作。

## 一、适用范围

- 适用于本仓库中的所有代码变更、功能开发、修复、重构和文档更新。
- 适用于项目内的 Python、前端、脚本、配置和辅助工具开发。
- 对于简单改动，可适当放宽流程，但仍应保持"最小变更、明确目标、可验证结果"。

## 二、核心规范

- 所有注释、提交说明、验证结果均使用中文；语言要简洁、准确、专业。
- 代码应保持"小而清晰"的函数/模块设计，避免冗长函数、重复实现、过度耦合。
- 变量、函数、类命名要明确；优先复用现有模式、工具、库和项目中已有实现。
- 代码注释至少包含：功能概述、输入/输出、边界条件、异常处理和性能/安全注意事项。
- 不得引入未经项目使用或未经审核的新依赖；必要时先说明理由并征得确认。
- 绝不提交密钥、凭证、敏感信息或硬编码隐私数据。
- 假设需显式说明；如有歧义，先提问而非自行决定。
- 不做"未被请求的灵活性"：不会为单次需求引入额外配置或抽象。

## 三、代码原则

### 1. Think Before Coding（先思考再编码）

- 明确假设与不确定性，必要时向用户确认。
- 列出可能的解释或实现路径，不要默默选择一种含糊解读。
- 如果存在更简单可行方案，应主动提示并推导。
- 遇到不清楚的地方，要停止并提出问题，而不是继续猜测.

### 2. Simplicity First（简单优先）

- 只写满足当前需求的最小代码，不要添加额外特性。
- 不为单次使用的逻辑创建复杂抽象。
- 不为"可能发生但实际不可能"的场景编写冗余代码。
- 如果 200 行可以用 50 行解决，就必须重写更简洁的版本。
- 代码复杂性应受"高级工程师是否会认为过度设计"这一标准检验。

### 3. Surgical Changes（精确改动）

- 仅修改与当前需求直接相关的代码，不做无关联的附带改进。
- 保持原有风格，不因个人偏好大范围重构。
- 发现无关死代码时，可记录说明，但不擅自删除。
- 如果改动产生了新的未使用导入/变量/函数，要清理它们。
- 每一处变更应能够直接追溯到用户请求。

### 4. Goal-Driven Execution（目标驱动执行）

- 将任务转换为可验证的目标，而不是模糊指令。
- 为每个改动定义"完成标准+验证方式"。
- 优先先写测试或最小可运行验证，再让实现通过验证。
- 多步任务应按"步骤 → 校验"形式组织，循环推进。

## 四、执行流程：6A 工作流

1. Align（需求对齐）
   - 明确核心目标、边界范围、验收标准。
   - 输出《需求共识文档（CONSENSUS.md）》，包括：必实现项、建议项、暂不实现项、澄清记录、风险预警。

2. Architect（架构设计）
   - 设计模块划分、接口契约、输入/输出格式、技术选型。
   - 输出《架构设计文档（ARCHITECT.md）》，并用 Mermaid 绘制模块依赖图。

3. Atomize（任务原子化）
   - 按 INVEST 原则拆解任务，保持每个任务小且可独立验证。
   - 输出《任务清单（TASK.md）》，并绘制任务依赖 DAG。

4. Approve（方案审批）
   - 提交审批包：前 3 阶段文档 + 风险评估表。
   - 获得用户或负责人明确"同意执行"后继续。

5. Automate（自动化执行）
   - 代码实现遵循规范，优先复用现有组件。
   - 同时编写配套测试，优先采用单元测试或最小可运行验证。
   - 输出《执行日志（LOG.md）》，记录状态、耗时、问题与修复。

6. Assess（成果评估）
   - 输出《验收报告（ACCEPTANCE.md）》，包含需求覆盖矩阵、测试结果、优化建议。
   - 完成交付后进行自查，确认无语法错误、测试通过、无新增技术债务。

## 五、执行细则：敏捷 5S 个人规则

- Scope Lock：明确任务范围、技术约束、输出格式，避免一次性生成冗余内容。
- Skeleton First：先搭建功能骨架，再逐步填充具体逻辑与单元测试。
- Sync & Fix：生成后立即校验语法、逻辑、规范，出现问题及时反馈并修正。
- Self-test Driven：核心功能自带测试用例，测试覆盖正常/异常/边界场景。
- Snippet Bank：沉淀优质代码片段与提示词，便于后续复用和规范统一。

## 六、技能优先与项目对齐

- 检查本仓库是否存在 `.trae/skills` 或 `.claude/skills`，若有相关技能则优先按技能说明实现。
- 若技能和需求不完全匹配，需说明原因并保持独立实现同时遵循本规则。
- 量化交易相关问题及代码优先使用 `quant-all-star-team` 规则进行审核与实现。


## 七、验收与交付要求

- 交付时应提供关键变更的代码位置与引用说明，便于 Review。
- 若引入新逻辑或新模块，必须附带可运行的验证方式或测试命令。
- 结果总结以中文输出，包含"完成情况、验证结论、后续建议"。

## 八、规则验证判断

以下指标用于判断本规则是否有效执行：

- 变更范围小且集中，diff 中只包含请求相关改动。
- 实现前通过澄清或假设说明消除歧义。
- 代码不再出现无必要的抽象、配置、或复杂度膨胀。
- 改动后可直接运行验证，并附带最小测试。
- 若是简单任务，遵循"谨慎优先，但不强制全流程"的原则。

## 九、权衡说明

- 本规则偏向"谨慎优先、避免盲改"，但并不追求每次改动都做全流程文档。
- 对于简单修复或小改动，可适度简化流程，重点保证"明确目标、最小变更、可验证"。

## 十、环境配置

- 项目默认 Python 解释器路径：`E:\Conda_env\Qlib_env\python.exe`（Qlib_env 虚拟环境，Python 3.12.12）
- 运行 Python 命令时，默认使用该解释器执行，避免用错 base 环境的 Python。
